# DO..WHILE implementation plan

## Goal and language contract

Add a post-test loop with this syntax:

```sinistra
@a = 0;
DO
  sys.log{@a};
  @a++;
WHILE @a < 5;
```

`DO statements; WHILE condition;` behaves like
`WHILE condition DO statements; ENDWHILE;` except that the body executes
before the first condition test. The body therefore executes at least once.
After each body execution, a true condition starts the body again and a false
condition exits the loop.

The new loop:

- uses the existing truthiness rules;
- permits an empty body, consistently with the existing empty `WHILE` body;
- permits nesting with `IF`, `WHILE`, and other `DO..WHILE` statements;
- exits immediately on `RETURN`, without evaluating another condition;
- is a statement and does not produce a result;
- discards expression-statement values inside its body;
- makes locals assigned in its guaranteed first body execution available to
  its condition and following statements; and
- does not change bytecode opcodes, the bytecode format, or runtime decoding.

Internally, use a distinct `N_DOWHILESTMT` AST node. Keep the same AST field
shape as `N_WHILESTMT` (`lhs` condition, `rhs` body), while explicitly visiting
and lowering the body before the condition.

## Phase 1 — discovery and complete plan

- Trace existing `WHILE..DO..ENDWHILE` handling through lexer, parser, AST
  lifecycle/debug walking, semantic analysis, lowering, bytecode verification,
  interpreter tests, fixtures, and documentation.
- Record syntax, semantic ordering, affected files, acceptance criteria,
  validation, agent count, and commit boundaries.
- Create an isolated feature branch.
- Commit this plan and stop for review.

## Phase 2 — complete bounded implementation

Use one isolated Luna implementation agent for the whole coherent feature.
The root agent reviews every diff and test result before committing.

### Compiler front end

- Reuse the existing `TDO` and `TWHILE` lexer tokens; add no keyword or lexer
  rule.
- Add the parser production `TDO stmtlist TWHILE expr`.
- Add `N_DOWHILESTMT` at the end of `ENUM_NODE` so existing node values do not
  shift.
- Update AST destruction, node-name tables, and debug walking.
- Add explicit semantic traversal in execution order: body, then condition.
  This must accept a local first assigned in the body and used by the
  condition.

### Lowering

- Lower with existing labels and jump IR:

  ```text
  start:
    body
    condition
    jump-if-false end
    jump start
  end:
  ```

- Reuse or narrowly factor the existing while-loop lowering only when that
  makes the ordering clearer; avoid unrelated refactoring.
- Keep body expression statements in discard mode, exactly like `WHILE`.
- Add no IR operation, bytecode opcode, verifier rule, emitter change, or
  runtime opcode.

### Focused coverage

- Extend parser allocation-cleanup coverage so the new AST is destroyed on
  every parser failure path.
- Add a malformed `DO..WHILE` case requiring a condition.
- Add semantic coverage proving a body-defined local is valid in the
  condition.
- Add lowering allocation-failure coverage.
- Add one source-pipeline golden fixture whose bytecode demonstrates
  body-before-condition control flow; register it through the existing
  pipeline case table and fixture policy.
- Add the source to compiler-emitted bytecode verifier coverage.
- Extend the existing interpreter result-semantics test with:
  - a false initial condition that still executes the body once;
  - a condition that repeats until the example counter reaches five; and
  - confirmation that a final `DO..WHILE` statement and its body expressions
    do not become the code-item result.
- Avoid new test functions where an existing matrix or result-semantics test
  is the natural home.

### Documentation

- Document the syntax, at-least-once behavior, truthiness, and example in
  `docs/concepts.md`.
- Include `DO..WHILE` in the statement-result rules in `docs/runtime.md` and
  `docs/bytecode.md`.
- Update `tests/TEST_COVERAGE.md` for the new focused coverage.

### Phase acceptance

- Bison reports no new conflicts.
- The user example parses and equivalent counter behavior reaches five.
- A false first condition still leaves a one-iteration side effect.
- Body-defined locals are accepted in the condition.
- Malformed syntax fails during parsing with deterministic diagnostics.
- Generated bytecode passes the existing verifier.
- Existing `WHILE` behavior and fixtures remain unchanged.
- `make test` passes.
- Commit the feature as one coherent language change. Any incidental bugfix
  or refactor must be a separate commit.
- Stop after root review, targeted validation, and commit.

## Phase 3 — independent integration review

Use one read-only Luna reviewer covering both specification compliance and
integration quality. Review the feature commit against this plan, with
particular attention to:

- grammar ambiguity and nested-loop parsing;
- AST ownership and allocation-failure cleanup;
- semantic body-before-condition ordering;
- label binding, jump direction, and statement-value discards;
- verifier compatibility and unchanged bytecode format;
- meaningful, non-duplicated positive and negative tests; and
- documentation matching actual syntax and results.

Resolve any substantive finding with one focused correction turn and a
separate correction commit when appropriate, then re-review. Run only the
narrow tests needed for a correction. Stop when the review is clean.

## Phase 4 — final validation and release readiness

- Run `make test`.
- Run `./ci/gate_sanitizers_fuzz.sh` outside the ptrace-restricted sandbox.
  This supplies strict-warning, release, leak-enabled ASan/UBSan, and seeded
  compiler/runtime/object-loader fuzz coverage without duplicating those gates.
- Inspect final commit boundaries, fixture changes, documentation, and
  `git diff --check`.
- Report all commands and any environmental limitations.
- Mark the branch ready only if the worktree is clean, review has no open
  findings, and every gate passes.

## Agent and token budget

- Phase 2: one Luna implementation agent.
- Phase 3: one Luna read-only reviewer; reuse it for re-review if needed.
- No other subagents unless a concrete blocker cannot be resolved by focused
  root inspection.
- Handoffs use this plan plus only the relevant files and observed failures;
  no conversation transcript or broad context dump.
