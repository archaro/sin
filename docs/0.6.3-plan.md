# Sinistra 0.6.3 Release Plan

Version 0.6.3 is the final planned release in the 0.6 series. This plan keeps
the release deliberately small: one bounded persistence fix, documentation
accuracy and troubleshooting improvements, and release validation. It does not
change the language, bytecode, or itemstore formats.

## Baseline

- Planning starts from commit `1a83ce7`, tagged `0.6.2`, on a clean `main`
  branch matching `origin/main`.
- The standard debug build and all 226 registered tests pass, as do the
  standalone network and localhost chat-smoke tests run by `make test`.
- The 0.6.2 work concentrated on task/network introspection and libcall-test
  organization. The 0.6.3 work should remain at that scale.

## Selected work

### Preserve every successful `sys.backup`

`lc_sys_backup()` currently derives its target only from a timestamp with
one-second precision. A second backup in the same second therefore replaces
the first backup through the normal atomic persistence path.

For 0.6.3, preserve the current readable timestamp as the base name and choose
a deterministic numeric suffix when that target already exists. Do not change
the primary itemstore format or persistence guarantees. Add regression
coverage proving that an existing same-timestamp file is not replaced and that
the new backup remains loadable. Update the `sys.backup` documentation with the
collision rule.

Expected files:

- `src/libcall/libcall_sys.c`
- `tests/core/test_libcall_sys.c`
- `docs/libcalls.md`
- `docs/concepts.md`

### Make the final 0.6 documentation accurate and useful

The public `sys.version` descriptions still give `"0.6"` as the current value
while `src/version.h` contains `"0.6.2"`. Remove the duplicated literal and
point readers to the version constant so the text cannot drift again.

Add a concise troubleshooting page covering:

- compiler diagnostic fields and stable codes;
- runtime `error` and `error.*` items;
- normal, quiet, verbose, and file logging;
- safe handling of an unreadable itemstore; and
- resetting generated itemstore/source-root state during local experiments.

Link the page from the documentation index and mark the corresponding roadmap
item complete. Correct `tests/TEST_COVERAGE.md`, which currently claims there
is no in-tree compiler fuzz target even though `tests/fuzz/fuzz_scomp.c` and
the documented fuzz targets provide one. Keep the remaining gap specific to
corpus and session diversity.

Expected files:

- `docs/troubleshooting.md`
- `docs/README.md`
- `docs/documentation-roadmap.md`
- `docs/concepts.md`
- `docs/libcalls.md`
- `tests/TEST_COVERAGE.md`

## Phases and stop gates

### Phase 1: baseline, audit, and plan

Review the tagged baseline, recent release history, architecture, coverage map,
documentation roadmap, persistence path, and relevant tests. Run `make test`.
Commit this plan and stop for review.

Acceptance:

- the selected work is supported by exact source/test evidence;
- deferred ideas and non-goals are explicit;
- the worktree is clean after the planning commit.

### Phase 2: backup uniqueness

Give the bounded implementation to one worker with an isolated handoff. The
worker must preserve unrelated changes, use test-first development, update the
runtime documentation, run the focused persistence/libcall coverage, and
commit the result. The root agent then inspects the diff and test evidence,
runs `make test`, and stops for review.

Acceptance:

- two backups cannot silently select the same target;
- a pre-existing timestamped backup remains byte-for-byte unchanged;
- the new backup is separately named and loadable;
- failure paths still return `false` and populate the existing persistence
  diagnostic contract;
- no on-disk format or unrelated libcall behavior changes.

### Phase 3: documentation and coverage truth

Give the bounded documentation task to one worker with an isolated handoff.
Review every statement against the current tools, diagnostics, runtime error
items, and tests. Commit the documentation slice and stop for review.

Acceptance:

- no public page hard-codes a stale current version;
- troubleshooting commands and reset guidance are safe and reproducible;
- the documentation index and roadmap agree;
- the coverage map describes the existing compiler fuzz harness and the actual
  remaining gap.

### Phase 4: release candidate and broad validation

Update `SINVERSION` to `0.6.3` in a focused commit, then run the release gates.
Fix only regressions caused by the selected work and commit each bounded fix.
Stop after reporting the complete validation evidence.

Required checks:

- `make test`
- `make test-warnings`
- `make test-release`
- `make test-lsan` outside a ptrace-restricted sandbox
- `FUZZ_SEED=1 make fuzz-smoke`

Acceptance:

- all required checks pass;
- `sin`, `scomp`, `sdiss`, and `sys.version` report `0.6.3`;
- tracked source contains no stale 0.6.2 user-facing version claim;
- the worktree contains no generated or build artifacts.

### Phase 5: final review and release-readiness report

Review the complete diff from tag `0.6.2`, confirm commit boundaries and
documentation/test coverage, and report release readiness. Do not create or
push a tag unless explicitly requested.

Acceptance:

- no unresolved correctness or release-blocking review finding remains;
- the final report lists changed files, commits, validation, documentation and
  fixture effects, and any checks not run;
- the branch is clean and ready for the user's release decision.

## Workflow and commit policy

- Use one implementation worker at a time and only one independent reviewer
  when the risk justifies it. The root agent owns scope, review, validation,
  and the final decision.
- Use the least costly accessible model for bounded exploration and mechanical
  work. Follow the repository's required DeepSeek-first transport for
  non-trivial code implementation.
- Stop after every phase. Do not start the next phase until the user resumes
  the work.
- Keep commits phase-focused. Never combine the backup fix, documentation
  slice, version bump, or validation fixes in one catch-all commit.

## Deferred candidates

The audit also found unchecked allocation paths in
`src/itemstore/item_error.c` and `src/common/log.c`. They are worth addressing,
but reliable allocation-failure coverage would introduce new test seams and a
larger error-reporting contract review. Defer them to 0.7 unless a narrowly
reproducible failure makes them release-blocking.

Broader parser property testing, expanded runtime session diversity, new
language constructs, new bytecode or itemstore versions, and structural
refactors are outside 0.6.3.
